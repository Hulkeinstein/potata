# Potata 의류 쇼핑몰 어드민 개편 조사 보고서

조사 기준일: 2026-10-20. 대상: Potata 운영자. 목적: 화면 꾸미기가 아니라 상품 등록부터 재고 보충과 고객 응대까지 실제 업무를 처리하는 관리자 구조 결정.

## 결론

Potata에는 상품·재고·혜택·Q&A·운영 이슈의 기본 기능이 이미 있다. 그러나 기능에 도달하는 경로와 반복 작업 처리가 부족하다. **기존 API와 안전장치는 유지하고, 관리자 전용 화면 구조와 상품 작업 흐름부터 재설계하는 것이 적합하다.**

추천 기준은 Shopify의 목록 작업 방식, 카페24의 업무 구분, 무신사·29CM의 권한과 업무 대기열이다. 대형 플랫폼의 메뉴를 전부 복제하는 방식은 1인 운영에 맞지 않는다. 지금 필요한 작업은 간단히 보이고, 판매 시작에 필요한 주문·배송·정산 기능은 별도 단계로 확장해야 한다.

## 조사 범위와 해석 기준

- Shopify, 카페24, WooCommerce의 공식 운영 문서와 무신사·29CM의 공식 파트너 가이드를 중심으로 비교했다. 4910은 운영사 에이블리의 공개 설명을 참고했다.
- 모든 의류 회사의 비공개 본사 관리자에 접근한 조사는 아니다. Zara·H&M 등의 내부 ERP 기능이나 4910 판매자 화면 배치는 확인하지 않았으며 추정하여 채우지 않았다.
- 무신사·29CM 자료는 입점사 파트너 관리자에 관한 것이다. 플랫폼 본사의 전체 관리자와 동일하지 않다. Shopify·카페24는 자사몰 운영 도구이므로 Potata의 현재 단계와 비교하기 더 직접적이다.
- 기능 제공 범위는 요금제·앱·계정 권한·국가에 따라 다르다. 아래 기능 목록은 업계 운영 역량의 분류이지 모든 서비스에 기본 제공된다는 뜻이 아니다.
- 우리 상태는 현재 소스와 로드맵을 대조한 결과다. 이번 조사는 실제 운영자 화면에서 모든 클릭을 다시 수행한 사용성 테스트나 처리시간 측정은 아니다.

### 반복 작업을 줄이는 목록

Shopify는 조건을 적용한 상품 목록을 저장한 보기로 재사용하고 열을 조절하며, 선택한 상품에 일괄 작업을 수행한다. 관리자 목록 정렬과 고객 매장의 진열 순서는 별개의 설정이다. Potata도 관리자가 정렬한 목록 때문에 For You나 Shop의 고객 노출 순서가 바뀌지 않아야 한다. [공식 상품 목록 가이드](https://help.shopify.com/en/manual/products/searching-filtering)

### 재고와 입고를 구분하는 구조

Shopify는 재고를 보유·판매 가능·예약된 수량·판매 불가·입고 예정으로 나누고, 공급처 발주와 입고 처리를 지원한다. Potata의 현재 재고 수량과 수동 품절은 유용하지만 발주·입고 예정·주문 예약 수량을 모두 표현하는 계약은 아니다. 판매 시작 시 확장이 필요하며 지금 화면만 바꿔 기존 stock을 다른 의미로 해석해서는 안 된다. [재고 상태](https://help.shopify.com/en/manual/inventory-and-locations/fundamentals/inventory-states), [발주](https://help.shopify.com/en/manual/inventory-and-locations/purchase-orders)

### 진열과 상품 관리의 분리

카페24는 상품 정보 관리와 메인·분류별 진열, 자동 진열 및 진열 예약을 별도로 제공한다. Potata의 상품 활성 상태는 판매 노출 여부이지 홈 기획전 배치 전체를 제어하는 설정이 아니다. 브랜드 소개·홈 배너·For You 운영 정책을 바꾸려면 별도 진열/콘텐츠 관리가 필요하다. [카페24 자동 진열](https://support.cafe24.com/hc/ko/articles/7739021669529), [공식 메뉴](https://support.cafe24.com/hc/ko/articles/7751287019545)

### 권한과 운영 대기열

무신사·29CM는 대표 계정과 일반 계정을 구분하고 업무별 메뉴 접근 및 대시보드 데이터 노출을 제한한다. 29CM의 확인 필요 CS는 대시보드에서 찾아 상담 메모로 처리한다. Potata는 현재 1인 운영이므로 직원 초대 시스템을 먼저 만들 필요는 없지만, 이후 CS 담당자가 고객 정보나 정산을 모두 보게 만드는 구조는 피해야 한다. [계정·권한 가이드](https://partner-stage.one.musinsa.com/posts/basic-strategy/147), [CS 가이드](https://partner-stage.one.musinsa.com/posts/basic-strategy/94)

## 기능 전체 분류와 우선순위

다음 표는 개편 백로그의 분류다. 업계 확인 기능은 위 공식 자료를 근거로 하고, Potata 특화 항목은 제안이다. 이 표의 P0는 개편 기반, P1은 현재 운영 효율 또는 판매 전 필수, P2는 확장을 뜻한다. 메인 로드맵의 장애 심각도 P0와는 다른 개편 내부 순서이며 현재 긴급 장애가 있다는 의미가 아니다. 후속 실행 계획에서는 단계 이름으로 구분한다. 판매 연동은 별도 승인 후다.

| 고객지원 | 미답변 Q&A, 답변, 리뷰, 문의 유형·상태, 담당·내부 메모 | Q&A 있음, P1 확장 |
| 콘텐츠 | OOTD·리뷰 신고, 숨김/복원, 조치 사유 | 별도 정책 후 P1/P2 |
| 혜택 | 쿠폰 캠페인, 발급 대상, 최소 금액·할인 한도·브랜드, 회수 | Pilot 있음, P0 UX 정리 |
| 혜택 분석 | 사용률, 할인 비용, 포인트 부채·소멸·사용, 중복 적용 | checkout 연동 뒤 |
| 분석 | 판매·재고·상품·고객·유입·전환·반품·이익 | 실제 데이터 연결 단계 구분 |
| 정산 | 결제대사, 지급 예정·완료, 수수료·환불·세금 | 매출과 별개, 판매 연동 단계 |
| 다국어 운영 | 상품별 EN/KO 누락, 번역 미리보기 | 기존 설명 재사용 P1 |
| AI 운영 | 설정 준비 상태, 생성 성공/실패, 사용량·비용 한도 | Try-On과 별도 P2, 사진 비노출 기본 |
| 보안 | 서버 권한, 재인증, 감사, 내보내기 제한, 직원 역할 | 기존 보호 보존, 직원 기능 후순위 |
| 시스템 | 연결 상태, 오류, 데이터 갱신 시각, 백업 절차, 실패 작업 | 일부 health 있음, P1/P2 |

의류 실측·소재·세탁 등은 운영자에게 원자료가 있어야 한다. 자동 채움으로 허위 정보를 만들지 않는다. CSV·대량 작업·직원 권한·정산은 화면 추가만으로 끝나는 기능이 아니다.

## 매출과 판매 순위 지표 설계

“토탈 인컴”이라는 이름 하나에 매출·수금·이익을 섞으면 판단이 어려워진다. WooCommerce도 매출·환불·할인·세금·배송을 나누고, Shopify의 이익 보고서는 판매 당시 원가가 있어야 한다. Potata는 다음처럼 별도 정의를 갖추는 것이 좋다. [WooCommerce 지표 정의](https://woocommerce.com/document/woocommerce-analytics/), [Shopify 원가와 이익](https://help.shopify.com/en/manual/reports-and-analytics/shopify-reports/report-types/default-reports/profit-reports)

| 지표 묶음 | 표시할 항목 | 계산에 필요한 데이터 |
| --- | --- | --- |
| 판매 | 확정 주문 수, 판매 수량, 순판매 수량, 누적 판매량 | 승인한 결제/주문 상태, 환불 수량 |
| 매출 | 할인 전 상품 금액, 할인액, 환불액, 순상품매출 | 주문 시점 금액, 할인 배분, 환불 원장 |
| 결제·현금 | 실제 수금, 환불 지급, 정산 예정·입금액 | 결제 이벤트, provider 지급·수수료 |
| 이익 | 매출총이익, 마진율, 비용 반영 수익 | 판매 당시 원가, 물류·수수료·운영비 범위 |
| 순위 | 상품·옵션·브랜드·카테고리 매출/수량 순위 | 기간, 취소·환불 포함 기준, 동률 처리 |
| 고객 | 신규/재구매 고객, 객단가, 재구매율, 고객별 누적 구매 | 개인정보 최소화한 구매 이력 |
| 재고 | 저재고, 품절, 판매소진율, 재고회전, 예상 소진일 | 기간 판매량, 평균/기초 재고, 입고 기록 |
| 전환 | 목록→상세→찜/장바구니→checkout→결제 | 중복 제거 이벤트, 세션, 동의·봇 기준 |
| 발견 피드 | 상품 노출·상세 이동·저장·브랜드 이동 | 화면상 실제 노출 이벤트, 분모 정의 |
| CS | 미답변, 응답 소요, 반품 사유, 취소·환불률 | 문의/클레임 생성·처리 시각과 유형 |
| 프로모션 | 쿠폰 사용 수·할인 비용·캠페인별 성과 | 발급이 아닌 실제 사용·주문 연결 |
| AI | 요청·성공·실패·지연·비용 | provider 상태와 실제 과금, 개인정보 분리 |

Potata 제안 정의: 순상품매출은 세금·배송비 제외 상품 총액에서 상품 할인·상품 환불을 차감한다. 매출총이익은 순상품매출에서 해당 판매 원가를 차감한다. 이것을 최종 순이익이라고 부르지 않는다. 수금은 결제 수취, 정산은 provider 입금이므로 각각 별개다.

모든 지표에는 기간·통화 AED·시간대 Asia/Dubai·집계 기준·갱신 시각이 필요하다. 전기 값이 0이면 증가율을 무한대로 표시하지 않고 비교 불가로 표시한다. 판매/반품 기준일과 분모도 설명한다. 공급 업체별 지표 정의를 그대로 섞어 비교하지 않는다.

현재 PENDING 주문·상품 조회수·찜을 실제 판매량으로 계산하지 않는다. 연결 전 지표는 “데이터 미연결”로 표시하고 가짜 차트나 0 매출을 실제 결과처럼 내보내지 않는다. 필요한 화면 자리는 분석 메뉴에 두되 현재 홈의 할 일을 밀어내지 않게 한다.

주문 처리 지표에는 배송 완료와 처리 소요도 포함할 수 있다. Shopify의 주문 분석 역시 주문량뿐 아니라 처리·배송·반품 지표를 연결한다. [주문 분석](https://help.shopify.com/en/manual/fulfillment/managing-orders/analytics/order-analytics)

## 추천 화면 구조

1인 운영 기본 언어는 한국어로 유지한다. 고객용 네온·쇼핑 탐색 화면과는 분리하고, 높은 대비·읽기 쉬운 숫자·밀도 조절 가능한 표를 사용한다. 다크/라이트 선택은 작업 화면의 실제 가독성 테스트 후 결정한다.

```text
POTATA 관리자
├─ 운영 홈              오늘 할 일, 바로 처리, 최근 변경
├─ 상품                 상품 목록, 등록, 브랜드, 사진과 정보 누락
├─ 재고                 옵션 재고, 저재고, 조정 이력
├─ 고객지원             상품 문의, 리뷰와 신고
├─ 혜택                 쿠폰, 포인트
├─ 콘텐츠와 진열        기획전, 홈, 브랜드 소개       확장
├─ 주문과 배송          주문, 출고, 클레임          판매 연동 후
├─ 분석과 정산          실제 지표, 보고서           데이터 연결 후
└─ 설정과 운영 기록     연결 상태, 감사, 운영 정책
```

### 운영 홈

첫 화면은 “오늘 처리할 일”을 우선한다. 미답변 문의, 저재고 옵션, 판매 중인데 필수 정보가 빠진 상품을 우선순위와 함께 보여준다. 누르면 같은 조건이 걸린 목록으로 이동한다. 기존 운영 어시스턴트를 재사용하고 동일 감지기를 새로 만들지 않는다.

처리할 일이 없으면 “대기 업무 없음”을 보여준다. 데이터 조회 실패를 업무 0건으로 바꾸지 않는다. 판매 중지·치수 미등록은 운영 의도일 수 있으므로 무조건 긴급 오류로 분류하지 않는다. 이슈 보류는 실제 데이터 문제를 고친 것과 구분한다.

### 상품 목록과 편집

목록 기본 열은 체크박스·사진·상품/브랜드·판매가·노출/품절 상태·옵션 재고 요약·정보 누락·수정 시각·작업이다. 상품을 열었다 돌아와도 검색·페이지·필터·스크롤을 보존한다. 모바일에서는 핵심 열만 카드로 요약하고 상세 편집으로 연결한다.

편집은 기본 정보 / 사진 / 한·영 설명 / 옵션 / 치수 / 노출 상태로 묶는다. 등록·수정의 공통 입력 계약을 공유하되 기존 ID·주문·리뷰·찜·태그 참조를 유지한다. 재고는 기존 조정 원장을 거치며 편집 저장으로 수량을 덮어쓰지 않는다.

이미지 교체는 새 파일 검증·저장과 상품 연결 성공을 먼저 확인한다. 이전 파일 정리는 공유 참조 여부를 확인한 뒤 수행하고 실패 업로드 고아 파일을 추적한다. 미리보기만 바뀌었는데 저장된 것처럼 표시해서는 안 된다.

### 재고와 일괄 작업

상품을 사진으로 식별한 다음 색상×사이즈 행에서 입고·정정·폐기를 선택한다. 전후 수량과 사유를 미리 보여주고 완료 후 원장으로 확인한다. 재고 부족 기준은 현재 1~3개와 맞추며 재고 0·수동 품절과 구분한다.

일괄 처리에는 선택 범위, 변경 전후 미리보기, 성공/실패 건수, 재시도 중복 방지가 필요하다. 현재 페이지 선택과 검색 결과 전체 선택은 구별한다. CSV는 미리 검증하고 실패 행을 내려받게 한다. 원장과 동시 변경을 무시하는 단순 stock 덮어쓰기는 도입하지 않는다. [Shopify 일괄 작업](https://help.shopify.com/en/manual/shopify-admin/productivity-tools/bulk-actions), [재고 CSV의 덮어쓰기 보호](https://help.shopify.com/en/manual/inventory-and-locations/setup/inventory-csv)

### 문의와 혜택

Q&A는 상품 사진·질문·대기 시간·답변 상태를 같은 맥락에서 보여준다. 답변 저장 후 다음 미답변으로 이동할 수 있게 한다. 템플릿 답변은 자동 발송하지 않고 운영자가 확인한다.

쿠폰과 포인트는 한 화면의 긴 폼으로 섞지 않는다. 캠페인 생성·발급·대상 확인·회수를 업무별로 나누고, 최종 실행 화면에서 대상 수·브랜드 범위·기간·금액·감사 사유를 확인한다. 기존 재인증·fingerprint·감사·취소 확인을 유지한다. 카페24 역시 쿠폰 종류와 지급 조건을 운영 기능으로 구분한다. [쿠폰 관리](https://support.cafe24.com/hc/ko/articles/7750336368665)

## 실제 운영 시나리오로 보는 개편 기준

| 업무 | 개편 후 기대 흐름 | 확인 기준 |
| --- | --- | --- |
| 사진 잘못된 기존 상품 수정 | 검색 → 사진 교체 → 저장 → 고객 미리보기 | ID/리뷰/찜 유지, 재등록 불필요 |
| 신상품 여러 개 준비 | 초안 작성 → 누락 보기 → 검증 → 선택 공개 | 불완전 상품이 자동 공개되지 않음 |
| 품절 보충 | 홈 저재고 → 상품/옵션 → 입고 → 이력 | 필터 유지, 중복 입고 없음 |
| 영문 설명 누락 보완 | 저장한 누락 보기 → 설명 탭 → 저장 | 기존 한국어 원문 보존 |
| 고객 질문 처리 | 미답변 → 상품 맥락 → 답변 → 다음 문의 | 중복 답변 방지, 실패 초안 유지 |
| 전체 쿠폰 발급 | 캠페인 → 대상 미리보기 → 재인증 → 발급 | 대상 수와 실제 결과 일치 |
| 판매 순위 확인 | 분석 → 기간·지표 → 상품/옵션 상세 | 결제 없는 데이터를 매출로 오인하지 않음 |

클릭 수와 처리 시간 개선률은 현재 측정하지 않았으므로 수치로 약속하지 않는다. 구현 전 동일 과제를 현재 화면에서 수행해 기준을 기록하고, 개편 후 같은 데이터로 비교해야 한다.

## 개편 실행 순서 제안

### 첫 단계는 관리자 기반과 핵심 반복 작업

- 독립 Admin Shell, 한국어 사이드바, 현재 위치·검색 조건 보존.
- 운영 홈을 할 일 중심으로 재구성하고 현황 링크를 연결.
- 상품 목록의 사진·상태·검색·필터와 편집 정보 구조 개선.
- 기존 상품 이미지 교체와 저장 피드백을 완성.
- 기존 Q&A·혜택·재고 도메인은 이전하고 보안 계약은 그대로 유지.

### 두 번째 단계는 상품 수 증가에 대응

- 한/영 설명·이미지 누락 보기, 저장한 보기, 선택 일괄 작업.
- 재고 DB 필터/페이지 처리, 옵션 중심 빠른 작업.
- CSV와 초안·발행 계약, 브랜드 원장·사진 관리는 데이터 모델 검토 후 진행.

### 세 번째 단계는 판매 운영

- 결제 정책 확정 후 주문·재고 예약·배송·교환·부분 환불·정산을 연결.
- 반품과 환불은 같지 않다. 회수·검수·재입고와 돈을 돌려주는 사건을 구분한다. [Shopify 반품과 교환](https://help.shopify.com/en/manual/fulfillment/managing-orders/returns/creating-returns)
- 회원별 구매·문의·혜택 맥락과 개인정보 권한을 연결.

### 네 번째 단계는 분석과 자동화

- 실제 판매·환불·원가·행동 이벤트를 기반으로 지표를 연결.
- 저재고·장기 미답변 알림, 보고서 내보내기, 담당자 역할·감사 조회 확장.
- 자동 가격 변경·쿠폰 발급·상품 숨김은 기본으로 실행하지 않는다. 미리보기·승인·감사를 먼저 마련한다.

## 반드시 유지할 안전 기준

- 기존 상품·사용자·주문·재고·혜택 데이터를 초기화하지 않는다. UI 전면 개편이 DB 전면 재작성 승인은 아니다.
- 서버 관리자 권한·혜택 재인증·원장·idempotency·동시성 보호를 재사용한다.
- 데이터 미연결, 실제 0건, 조회 실패를 구별한다.
- 사용자 사진·개인정보·메일 주소를 홈·분석에 무분별하게 노출하지 않는다. CSV는 별도 권한과 감사 대상이다.
- 고객 자동 갱신/For You 정렬 계약은 관리자 목록의 정렬·필터 변경과 분리한다.
- 비밀키를 관리자 브라우저로 전달하거나 일반 설정 폼에 저장하지 않는다.
- 프런트엔드 메뉴 숨김만으로 권한을 대체하지 않는다.
- 실제 매출이 없는 기능은 준비 상태를 정직하게 표시한다. 작동하지 않는 메뉴를 완료처럼 만들지 않는다.

## 이번 조사 결과와 다음 결정

현재 가장 효과적인 개편 단위는 **독립 관리자 화면 + 업무 중심 홈 + 상품 목록/이미지 편집**이다. 이 묶음이 현재 상품 확충과 직접 연결되며, 새 결제나 유료 운영 도구 없이도 시작할 수 있다.

후속 구현 계획에서는 이 첫 묶음의 화면 구성과 데이터 계약을 고정하고 기존 관리자 경로별 이전표를 만든다. 새 브랜드 원장·초안 상태·CSV·주문 시스템을 동시에 포함하는 일괄 재작성은 피한다. 지금은 조사 보고서 작성 단계이며 코드·DB·외부 설정·커밋·배포는 변경하지 않았다.
